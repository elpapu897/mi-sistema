# Auditoría TESTER — bloqueantes de compra
Fecha: 2026-08-17
Modo: auditoría / borrador. No se pagó, no se publicó, no se mandaron mensajes y no se modificaron campañas.

## Resumen ejecutivo

Encontré tres bloqueantes o riesgos confirmables desde la tienda pública:

1. Checkout: el checkout expone simultáneamente `paypal`, `Mercado Pago Checkout Pro` y `Credit/Debit card by PayPal`. La tercera opción se presenta al comprador como “Pagos con tarjeta de crédito y débito”, aunque pertenece a PayPal. Esto mantiene el riesgo documentado de que una persona intente pagar con tarjeta argentina y falle.
2. Píxel: en el HTML público de la home aparece el ID `3919766821491073`, pero no aparece el dataset de referencia `26889872433954472`. En la evidencia pública obtenida no pude confirmar el píxel bueno ni una unificación. Esto es consistente con el riesgo de duplicación/desalineación documentado en CONTEXTO.
3. Política de envíos: `https://gonvra.com/policies/shipping-policy` devuelve HTTP 404. El enlace está roto y deja sin respaldo visible la promesa de envío.

El recorrido técnico básico home → producto → carrito → checkout responde correctamente por HTTP y permite abrir el checkout sin pagar. No pude hacer una prueba visual real de móvil/desktop porque el navegador automatizado no estaba abierto ni pudo iniciarse; sí hice comprobaciones HTTP con user-agent de desktop y de iPhone.

## Evidencia reproducible

Fuente de catálogo vivo consultada: `https://gonvra.com/products.json?limit=250`.

- 15 productos publicados.
- Todas las variantes devueltas por el catálogo vivo figuran `available: true` en la consulta realizada.
- Rango de precios observado: $5.990 a $42.990.
- Productos de ticket >= $16.990: 11 de 15 productos (contando productos, no variantes). No se usaron productos históricos: los nombres, variantes y precios de este informe salen de la respuesta viva de Shopify.
- Ejemplo usado para probar el flujo: `Kit Aseo Total Perro 🐶 — Baño + Patas + Dientes`, variante `51696653631783`, precio vivo $31.990.

Recorrido:

- `GET https://gonvra.com` → HTTP 200.
- `GET https://gonvra.com/products/kit-aseo-total-perro` → HTTP 200.
- `POST https://gonvra.com/cart/add.js` con una unidad de la variante viva → HTTP 200.
- `GET https://gonvra.com/cart.js` → HTTP 200, moneda ARS; la sesión de prueba quedó local y no se envió ninguna orden.
- `GET https://gonvra.com/checkout` → HTTP 302 hacia checkout Shopify.
- Checkout final → HTTP 200, sin completar pago.

Prueba de dispositivo:

- Desktop y iPhone user-agent: home, producto y carrito devolvieron HTTP 200.
- Ambos HTML incluyen viewport; esto solo verifica respuesta y estructura servida, no usabilidad visual ni interacción táctil.
- Intento de navegador: falló porque no había Chrome soportado abierto y el entorno no pudo lanzarlo. Por eso queda pendiente una revisión visual manual en un teléfono y una computadora.

Checkout:

El HTML del checkout contiene estos gateways:

- `paypal`
- `Mercado Pago Checkout Pro`
- `Credit/Debit card by PayPal`

También contiene el método visible `Pagos con tarjeta de crédito y débito`, con moneda disponible ARS. La evidencia prueba exposición/configuración, no una simulación de pago ni un error de cobro: no se ingresaron datos de tarjeta y no se realizó ningún intento de autorización.

Píxel:

- Home pública: aparece `3919766821491073`.
- Home pública: no apareció `26889872433954472` en la respuesta obtenida.
- En el HTML aparecieron referencias de eventos como `PageView`, `addToCart` y `purchase`, pero la presencia textual de nombres no prueba que estén disparándose correctamente en Meta ni que haya conversiones reales.
- No pude confirmar AddToCart/Purchase en Meta porque no tengo una sesión de Ads Manager disponible desde este entorno y no corresponde ejecutar acciones externas.

Política:

- `GET https://gonvra.com/policies/shipping-policy` → HTTP 404.
- La home declara envío gratis a todo el país en el título/descripción; con la política 404, la promesa queda sin una página accesible de respaldo.

## Impacto estimado en pesos

No hay datos de intentos fallidos ni ventas atribuidas en esta prueba, así que no presento pérdida histórica como si fuera un hecho.

Escenario de riesgo para checkout: tomando el ticket esperado documentado de $20.000–$32.000, 10 intentos que eligieran la opción de tarjeta PayPal y fallaran pondrían en riesgo aproximadamente $200.000–$320.000 de facturación bruta potencial. Es una simulación para dimensionar, no una medición de ventas perdidas.

Píxel: sin medición confiable, el impacto directo no se puede calcular. Como referencia operativa, cada venta no atribuida impide aprender qué anuncio funciona y puede hacer que se asignen pesos a señales incorrectas. No se inventa un monto sin datos de inversión/ventas.

Política 404: el impacto directo tampoco es medible con la evidencia disponible. Puede aumentar dudas y abandono antes del pago; el monto en riesgo depende de sesiones y conversión reales.

## Acción propuesta

Prioridad 1 — REVIEW + SEMÁFORO:

1. Matías debe revisar manualmente Shopify → Configuración → Pagos.
2. Desactivar `paypal` y `Credit/Debit card by PayPal` si siguen habilitados para compradores argentinos.
3. Dejar activo `Mercado Pago Checkout Pro` y hacer una prueba controlada sin completar pago, verificando que el checkout muestre ARS y que el redireccionamiento sea el esperado.
4. Revalidar el snapshot justo antes de cambiar cualquier configuración.

Prioridad 2 — REVIEW + SEMÁFORO:

1. Revisar en Shopify/Meta cuál dataset debe quedar como único.
2. Unificar la instalación para que quede el dataset bueno documentado (`26889872433954472`) y retirar el duplicado (`3919766821491073`) solo con confirmación de permisos y del lugar exacto de inyección.
3. Luego verificar PageView y ViewContent de forma no destructiva. No optimizar a Compra mientras no existan compras reales confirmadas.

Prioridad 3 — REVIEW + SEMÁFORO:

1. Publicar manualmente una política de envíos accesible en la ruta que usa el footer, o corregir el enlace del footer hacia la página real.
2. La política debe explicar envío gratis a Argentina, seguimiento, plazos reales y qué ocurre con zonas/domicilios problemáticos. No inventar plazos.
3. Volver a probar la URL desde móvil y desktop después de publicar.
